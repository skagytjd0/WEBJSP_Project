| **WIN-004** | 낙찰내역 | 낙찰 취소 처리 (관리자) | 낙찰자가 기한 내에 대금을 결제하지 않거나(미입금), 정당한 사유로 취소를 요청할 경우<br>관리자가 해당 낙찰 건을 취소 처리하고 경매 상태를 되돌린다 |

### 1.5 기능 요구 사항 - 입찰내역 (BID)

| 요구사항 ID | 요구사항분류 | 요구사항명 | 요구사항 상세 설명 |
| :--- | :--- | :--- | :--- |
| **BID-001** | 입찰내역 | 입찰 내역 조회 (회원) | 일반 회원이 메인 메뉴의 마이페이지를 통해 과거 자신이<br>어떤 상품에 얼마로 입찰에 참여했었는지 개인 입찰 이력 리스트를 필터링하여 조회한다. |
| **BID-002** | 입찰내역 | 상품별 입찰 현황 (관리자) | 관리자가 특정 경매 상품의 번호를 입력하면, 해당 상품에 들어온<br>모든 입찰 기록들을 금액이 높은 순서대로 정렬(Sort) 혹은 순회하여 화면에 출력한다. |

## 3. 요구사항명세 - 비기능

### 2.1 비기능 요구사항 - 데이터(DATA)

| 요구사항 ID | 요구사항분류 | 요구사항명 | 요구사항 상세 설명 |
| :--- | :--- | :--- | :--- |
| **DATA-001** | 데이터 | 경매품 정보 관리 | 등록된 모든 경매 물품 데이터는 ItemDAO 계층의 내부 딕셔너리(`self.__itemDB`)에 `[상품 고유번호(String) : Item 객체]` 구조로 저장 관리한다. 시스템 구동 시 초기화되거나 상품 추가/삭제 시 딕셔너리의 항목을 추가(insert) 및 삭제(pop) 처리하며, 프로그램이 실행되는 동안 메모리 상에서 데이터의 영속성 상태를 유지한다. |
| **DATA-002** | 데이터 | 회원 정보 관리 | 회원들의 계정 정보는 MemberDAO 계층의 내부 딕셔너리(`self.__memberDB`)에 `[회원 ID(String) : Member 객체]` 쌍으로 캡슐화하여 저장한다. `is_exist(id)` 메서드를 통해 키(Key)의 존재 여부를 실시간으로 대조하며, 회원 탈퇴나 관리자의 악성 회원 강퇴 처리 시 `__memberDB.pop(id)`을 호출하여 메모리 DB에서 완전히 격리 및 제거한다. |
| **DATA-003** | 데이터 | 문의사항 정보관리 | 회원들이 접수한 1:1 문의 및 답변 데이터는 InquiryDAO 계층의 내부 딕셔너리(`self.__inquiryDB`)에 `[문의 고유번호(int/String) : Inquiry 객체]` 형태로 매핑하여 보관한다. 시퀀스를 활용해 글 번호를 자동 발급하며, 회원의 ID 정보(`get_id()`)를 외래 키 형태로 결합하여 본인이 작성한 문의 글 목록만 리스트(`values()`)로 필터링하여 순회 출력할 수 있도록 제어한다.<br>관리자가 답변을 등록<br>문의 목록 조회는 회원은 자기것만 관리자는 모든걸 볼수있어야함 |
| **DATA-004** | 데이터 | 낙찰내역 정보관리 | 경매 마감 처리 시 발생하는 최종 낙찰 데이터는 WinningDAO 계층의 내부 딕셔너리(`self.__winningDB`)에 `[낙찰/주문 번호(String) : Winning 객체]` 구조로 저장한다. 각 낙찰 객체는 상품 번호(DATA-001)와 최종 승리한 회원 ID(DATA-002)를 멤버 변수로 가지고 있도록 매핑하여 관리하며, 결제 상태(Status) 변경을 통해 대금 지급 여부의 생명 주기를 제어한다. |
| **DATA-005** | 데이터 | 입찰내역 정보관리 | 경매 진행 과정에서 접수되는 실시간 입찰 데이터는 BidDAO 계층의 내부 딕셔너리(`self.__bidDB`)에 `[입찰 고유번호(int) : Bid 객체]` 구조로 누적 저장한다. 동일한 상품 번호에 대해 여러 회원의 입찰 객체가 누적될 수 있으며, BidService의 순회 정렬 로직을 통해 특정 상품의 현재 최고가 입찰 객체를 판별하고 최종적으로 DATA-004(낙찰내역)로 데이터를 전환(연동)시키는 기반이 된다 |
